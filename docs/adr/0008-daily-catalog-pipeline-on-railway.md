# Scheduled catalog pipeline on Railway cron

The searchable Catalog is rebuilt incrementally by Railway cron services. Scraped Auctionet Item JSON and Vector Artifacts are the durable intermediate state in a Railway Bucket (S3-compatible); Qdrant remains the source of truth for Reference vectors used at search time. The orchestrator (`pnpm cron`) selects stages with `--stages scrape,embed,store,upsert` (default: all four). Scrape writes item JSON straight to the bucket (`HeadObject` skip / `PutObject`). Indexing lists bucket keys page by page, reads one item into memory, checks deterministic Qdrant IDs, reuses a bucket Vector Artifact or embeds the item, uploads new artifacts immediately, and then upserts. No local item or vector files are required by the scheduled indexing pipeline. `store` is required with cron embedding so generated artifacts have a durable checkpoint before Qdrant writes. Standalone file-based embed/upsert commands remain available; a store-only cron run explicitly uploads existing local artifacts for recovery.

## Considered Options

- **Railway cron + bucket-backed intermediates** (chosen) — matches the existing scrape → embed → upsert scripts, survives ephemeral disks, and stays idle between runs.
- **Always-on worker with a local volume** — simpler resume on disk, but pays for idle compute and couples durability to one volume.
- **Re-scrape and re-embed everything daily** — no bucket skip checks, but wastes Auctionet fetches and OpenRouter spend.

## Consequences

The web service and catalog cron services must be separate Railway services. Both are declared in `.railway/railway.ts` (Railway Infrastructure as Code, which replaces the deprecated per-service `railway.toml` files). The `scrape` service runs every 30 minutes with `--stages scrape`. The separate `embed` indexing service runs hourly on the hour (UTC) with `--stages embed,store,upsert --max-embed-items 50`. Start with a manual single-category run, then an uncapped catch-up before enabling the schedule. The scheduled run embeds at most 50 new items across categories, including all images per item. Existing and unsold items do not consume this budget; failed embedding attempts consume a slot, and any failed item stops the run visibly. When upsert is selected, the embed stage also skips items fully indexed in Qdrant. Bucket keys live under `scrape/...` so they never collide with Query image Keys. Operators configure categories with `CATALOG_CATEGORIES` (default: the full Auctionet leaf taxonomy). A run that overlaps the next schedule is skipped by Railway, so each run's scrape/embed budget must fit inside its own interval (30 minutes for scrape-only) or use `--max-pages` / `--max-items` while bootstrapping.

The scheduled scrape uses backfill with a 500-new-item budget, enforced even with concurrent workers. Each category starts in oldest end-date order, then tries newest end-date and ascending/descending estimate order as needed to reach beyond an individual listing’s page cap. Remaining sort orders are skipped once unique discovered IDs match the advertised count. Pagination must move forward within the same category, filters, and sort order. Each pass logs why it stopped and its unique-item coverage. Duplicate Auctionet IDs are skipped within the run and existing item objects are skipped in the bucket; only newly saved items consume the budget. Runs restart listings rather than persisting page positions. An uncapped, unbudgeted completion must cover the advertised count; otherwise scraping fails visibly instead of silently accepting an incomplete archive. Sort-order unions cannot guarantee coverage for arbitrarily large categories; such failures require narrower filters.

Indexing checks expected Qdrant point IDs first when upsert is selected. Fully indexed items are skipped even without a bucket artifact; they are not re-embedded just to restore that artifact. Items with missing Qdrant points reuse saved bucket artifacts. Embed/store-only runs skip the Qdrant check and can regenerate missing artifacts without requiring Qdrant. Upsert-only runs enumerate existing bucket artifacts. `--force` rewrites Qdrant points from saved vectors without re-embedding indexed items. Bucket read errors never count as missing artifacts.

Uploading each artifact before upsert makes the bucket the recovery checkpoint: after Qdrant failure, the next run reuses the saved vectors. Upload failure stops the run before upsert; an embedding lost before a successful bucket upload may still need to be regenerated. The shared embedding budget stops processing after the final attempted item has been fully stored and upserted. Dry-run indexing reads bucket/Qdrant to plan work but makes no paid embedding calls or writes. Terminal progress includes listing pages, per-item actions, image batches, skip reasons, elapsed time, totals, and remaining embedding budget.

Embedding Failures also live in the bucket, including failures from the standalone local embed command. One object per item under `scrape/<category>/failures/<shard>/<auctionet-id>.json` records the item key, latest error, and timestamp; workers never rewrite a shared failure manifest. Failures before the Vector Artifact is saved are recorded, and successful saving or confirmed indexed References removes the record. Qdrant failures after saved vectors do not recreate embedding failures. Both commands accept `--retry-failed` to select only items listed by these objects; cron defaults to embed/store/upsert without scrape in this mode. Local embedding still consumes local inputs and writes local artifacts, but requires bucket access for its failure state. Dry runs never mutate failures, and bucket errors propagate. Existing failure logs are not automatically backfilled.

Parallelism uses one active worker per category, with disjoint `--category` or `CATALOG_CATEGORIES` assignments and separate Qdrant collections/bucket prefixes. No shared lock is added: overlapping category assignments (including an all-category worker plus category-specific workers) can duplicate paid embedding work. Budgets apply per process, while provider rate limits and Qdrant capacity are shared. Start with two or three workers. The Railway configuration retains the existing all-category hourly service until operators explicitly split its assignments into separate services; do not run both arrangements simultaneously.
